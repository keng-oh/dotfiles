# code-explain

ユーザーはコードを読んで**学んでいる**。目的は理解させることで、作業を進めることではない。
コードは変更しない。

## 1. 対象を決める

`$ARGUMENTS` から決める。無ければ `commit`(直近のコミット)とする。

| 引数 | 読むもの |
|---|---|
| `commit [ref]` | `git show --stat <ref>` と `git show <ref>`(既定 `HEAD`)。差分だけでなく、変更されたファイルの周辺も読んで文脈をつかむ |
| `file <パス>` | そのファイル全体と、それが呼んでいる・呼ばれている主な箇所 |
| `repo` | README、依存の定義(`go.mod`・`package.json` 等)、ディレクトリ構成、エントリポイント、主要なパッケージ。全行は読まず、構造と流れを説明する |

## 2. レベルを聞く

`AskUserQuestion` で毎回聞く:

- その言語の経験: 初めて / 少し書いたことがある / 普段使っている
- 解説の深さ: 要点だけ / 標準 / 徹底(背景の技術を物理層に近いところまで)

## 3. 読んで確かめる

- 言語仕様・標準ライブラリの挙動は記憶で書かず、確かめられるものは確かめる
  (Go なら `go doc <pkg>.<name>`、`go vet`、小さなコードをスクラッチで実行する、など)
- 確かめられなかった説明には「未確認」と書く

## 4. 解説の構成

レベルに合わせて各節の量を変える。経験者には文法の節を短く、初めての人には丁寧に。
コードを引用するときは `ファイル:行` を付ける。

1. **概要**: 何をするコードか。全体の流れを数行で
2. **なぜこう書くのか**: 設計判断と、考えられる別の書き方を選ばなかった理由
3. **文法**: 出てきた構文・慣用句を、初出のものだけ説明する
4. **ロジック・アルゴリズム**: 処理の流れ、使っているアルゴリズム・データ構造、計算量
5. **アンチパターン・注意点**: このコードに潜む問題点も遠慮なく指摘し、より良い書き方を示す。
   その言語でよくある落とし穴も、このコードに関係するものを挙げる
6. **背景の技術**: このコードを支えている層を、関係するものだけ下へたどる。
   例: ランタイム(goroutine のスケジューラ・GC・メモリモデル)→ OS(システムコール・
   ファイルディスクリプタ・プロセスとスレッド)→ ネットワーク(TCP・TLS・HTTP)→
   ハードウェア(CPU キャッシュ・メモリ・ディスク I/O)。ミドルウェア(DB・キュー等)が絡むならそれも
7. **確認問題**: 理解を確かめる問いを2〜3個(答えは折りたたみか末尾に)
8. **次に読むもの**: 公式ドキュメントや、このリポジトリ内で次に読むとよい箇所

## 5. 出力

**会話には要点だけ**を出す(概要・押さえるべき点3〜5個・保存先)。
**全文はファイルに保存**する:

```
${CODE_EXPLAIN_DIR:-~/notes/code-explain}/<リポジトリ名>/<YYYY-MM-DD>-<対象>.md
```

- `<対象>` は `commit-<短縮ハッシュ>`、`file-<パスを - でつないだもの>`、`repo` のいずれか
- ノートの冒頭に、リポジトリ名・対象・コミットハッシュ・日付・選んだレベルを書く
- 秘密(鍵・トークン・`.env` の値)や個人情報は、コードに含まれていてもノートに写さない

最後に、続けて質問してよいことを一言添える。質問に答えた内容で、ノートに残す価値が
あるものは追記する。
